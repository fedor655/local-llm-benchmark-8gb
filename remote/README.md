# Локальная LLM на удалённом ПК, доступная с телефона

Ставит на домашний Windows-ПК крупную модель без цензуры, раздаёт её через ваш
VPS и делает так, чтобы к ней можно было писать с телефона и подключать
агентов. Ключевая часть — **связь, которая не рвётся**.

```
   Телефон ───HTTP──▶ 31.76.72.214 : 80   (nginx)
                            │
                            ├─ /          ─▶ Open WebUI   (127.0.0.1:3000, docker)
                            ├─ /ollama/   ─▶ 127.0.0.1:11434 ─┐
                            └─ /llm-status.json               │  frps
                                                              │
                            ┌─────────────────────────────────┘
                            │  соединение устанавливает ПК, а не сервер
                            ▼
   ПК (Windows) ── frpc ──▶ 127.0.0.1:11434  Ollama + модель
                       └──▶ 127.0.0.1:22     sshd  (опционально, --EnableSsh)
```

---

## Почему не Tailscale в роли управляющего канала

Вы описали симптом: как только идёт подключение через Tailscale к ПК —
пропадает связь у самого подключающегося. Это не случайность, у Tailscale
две настройки, которые делают ровно это:

- `--accept-dns=true` (по умолчанию) — MagicDNS переписывает системный
  резолвер. Всё, что резолвилось до этого, перестаёт резолвиться.
- `--accept-routes` / `--exit-node` — заворачивает маршруты, в том числе
  тот, по которому вы сюда пришли.

Отсюда два вывода, оба заложены в эту схему:

1. **Управляющий канал не должен зависеть от Tailscale.** Здесь соединение
   всегда инициирует ПК наружу, к вашему серверу (`frpc`). Это переживает
   NAT, серый IP и смену адреса, и ничего не делает с маршрутами.
2. **Никаких длинных сессий.** `tools/rexec.sh` на каждую команду открывает
   новый коннект и гарантированно выходит: `-n`, `ControlMaster=no`,
   `ControlPath=none`, жёсткий `timeout`. Ровно тот режим «зашёл, выполнил,
   вышел», который вы просили.

Если Tailscale всё же нужен параллельно — поднимайте его так, чтобы он
не трогал сеть хоста:

```
tailscale up --accept-dns=false --accept-routes=false
# и никогда --exit-node на машине, с которой вы работаете
```

## Порядок запуска

Всё делается **с сервера**. К самому ПК подходить не нужно — до него
скрипт дотягивается через Tailscale и работает заходами.

### 1. Сервер: точка входа

```bash
scp -r remote root@31.76.72.214:/root/llm/
ssh root@31.76.72.214 'bash /root/llm/server/setup-server.sh'
```

Ставит Docker, `frps`, Open WebUI, настраивает nginx и публикует
`/llm-status.json`. В конце печатает `FRP_TOKEN` — он же остаётся
в `/etc/frp/token`, дальше подхватывается сам.

### 2. Сервер: разведка ПК

Ничего не меняет, только смотрит. Сначала убедимся, что связь есть
и железо то, что мы думаем:

```bash
ssh root@31.76.72.214
cd /root/llm/server
export PC_HOST=<имя ПК в тайлнете>   # или его 100.x.y.z
export PC_USER=<пользователь на ПК>
./provision-pc.sh recon
```

Напечатает ОС, процессор, объём RAM, видеокарту с объёмом VRAM,
свободное место, есть ли уже Ollama и есть ли у пользователя права
администратора.

### 3. Сервер: установка

```bash
./provision-pc.sh install
```

Заливает `setup-pc.ps1` на ПК и запускает его там: Ollama, подбор модели
под снятое железо, закачка, распределение RAM/VRAM, `frpc` в автозапуске.
Шаг долгий — качается 14–24 ГБ.

Обрыв связи на этом шаге не страшен: каждая команда идёт отдельным
заходом, а `ollama pull` докачивает с места обрыва. Просто запустите
`install` снова.

### 4. Проверка (откуда угодно)

```bash
./remote/tools/healthcheck.sh
```

Пять шагов: сервер → статус → API → ответ модели → вызов инструментов.
Код возврата 0 только если живо всё.

### Что нужно от вас заранее

- **Сервер в тайлнете.** Если его там нет — сгенерируйте ключ на
  `login.tailscale.com/admin/settings/keys` и передайте:
  `TS_AUTHKEY=tskey-auth-... ./provision-pc.sh recon`.
  Скрипт поднимет Tailscale с `--accept-dns=false --accept-routes=false`,
  чтобы не уронить сеть самого сервера.
- **Вход на ПК по SSH.** Либо Tailscale SSH, либо ключ, либо
  `PC_PASS=...` (тогда на сервере нужен `sshpass`).
- **Учётка на ПК — администратор.** Строка `ADMIN: True` в выводе
  `recon` это подтверждает. Сессии Windows OpenSSH получают полный
  админский токен, UAC их не режет, так что отдельного повышения прав
  не потребуется.

## Какая модель и почему

Железо из бенчмарка в корне репозитория: RTX 3070 Laptop 8 ГБ VRAM + 16 ГБ RAM.
Бюджет под модель — около 19 ГБ (5 ГБ забирает Windows).

| Модель | Размер | Активных параметров | Когда берётся |
|---|---|---|---|
| `huihui_ai/Qwen3.6-abliterated:35b-a3b-q4_K` | 24 ГБ | 3 B из 35 B | если RAM+VRAM ≥ 29 ГБ |
| **`huihui_ai/gpt-oss-abliterated:20b`** | **14 ГБ** | **3.6 B из 21 B** | **выбор по умолчанию** |
| `huihui_ai/qwen3-abliterated:14b` | 9 ГБ | плотная | запасной вариант |

Выбор по умолчанию не случайный. Главный вывод бенчмарка в этом репозитории —
**обрыв на 8 ГБ VRAM**: всё, что не влезло в видеопамять целиком, падает
с 40–75 tok/s до 6–13. Но обрыв бьёт по *плотным* моделям, где каждый токен
проходит через все веса. У MoE на каждый токен работают только 3–3.6 млрд
параметров из 21–35 млрд, поэтому слои, уехавшие в RAM, задействуются
редко — и выгрузка перестаёт быть приговором.

`gpt-oss:20b` в вашем же бенчмарке — первое место с 92.2 балла и
**единственная модель, решившая все 13 кодовых задач**. Здесь берётся её
abliterated-версия: те же веса, снят отказной вектор.

Перебить выбор вручную:

```powershell
.\setup-pc.ps1 -Model "huihui_ai/Qwen3.6-abliterated:35b-a3b-q4_K"
```

## Как раскладывается память

Скрипт ставит эти переменные Ollama на уровне машины:

| Переменная | Значение | Зачем |
|---|---|---|
| `OLLAMA_KEEP_ALIVE` | `-1` | Модель остаётся в памяти. Без этого Ollama выгружает её через 5 минут простоя, и следующий вопрос ждёт повторной загрузки 14 ГБ с диска — те самые «две с половиной минуты» из бенчмарка. |
| `OLLAMA_FLASH_ATTENTION` | `1` | Меньше памяти под внимание. |
| `OLLAMA_KV_CACHE_TYPE` | `q8_0` | KV-кеш вдвое меньше — освободившаяся VRAM уходит под слои модели. |
| `OLLAMA_NUM_PARALLEL` | `1` | Каждый параллельный слот множит KV-кеш. При 8 ГБ VRAM слот должен быть один. |
| `OLLAMA_CONTEXT_LENGTH` | `16384` | Компромисс: агенту нужен контекст, но он же ест VRAM. |

Сколько в итоге уехало на процессор — видно так:

```bash
./remote/tools/rexec.sh pc 'ollama ps'
```

Колонка `PROCESSOR` покажет что-то вроде `43%/57% CPU/GPU`. Если хочется
подвинуть границу вручную — `-NumGpu <число слоёв>`; ставьте на 2–3 меньше
того, при котором Ollama падает с ошибкой памяти.

## Агент

Ollama отдаёт OpenAI-совместимый API, поэтому подходит почти любой
агентский фреймворк:

```
BASE_URL = http://31.76.72.214/ollama/v1
API_KEY  = ollama          # любое непустое значение
MODEL    = agent
```

`agent` — профиль, который создаёт `setup-pc.ps1`: те же веса плюс
зафиксированные `num_ctx`, температура и системный промпт, чтобы клиенты
не задавали их каждый раз.

Вызов инструментов проверяется пятым шагом `healthcheck.sh` — он посылает
запрос с `tools` и ждёт `tool_calls` в ответе.

С телефона: открыть `http://31.76.72.214/` и добавить на домашний экран —
Open WebUI ставится как PWA и выглядит обычным приложением.

## Если после установки на сервере поплохело с сетью

Первое, что надо проверить, — политику цепочки `FORWARD`. Docker при
установке выставляет её в `DROP`. Пока сервер только отвечает на запросы,
это незаметно. Но если он **маршрутизирует** трафик — VPN-шлюз, WireGuard,
OpenVPN, проброс для домашней сети, — транзит после этого умирает, и
снаружи это выглядит как «интернет вдруг стал еле работать».

```bash
iptables -S FORWARD | head -1
```

`-P FORWARD DROP` — вот оно:

```bash
iptables -P FORWARD ACCEPT
# чтобы пережило перезагрузку:
apt-get install -y iptables-persistent && netfilter-persistent save
```

`setup-server.sh` теперь запоминает политику до установки Docker и
возвращает её, если Docker её сменил. На серверах, где Docker уже стоял,
скрипт её не трогает вовсе — значит, могло остаться с прошлого раза.

Снять всё установленное:

```bash
bash /root/llm/remote/server/rollback-server.sh
```

Возвращает прежний сайт nginx, удаляет frps и таймер статуса, чинит
`FORWARD`. Docker оставляет — на сервере могут быть чужие контейнеры;
`PURGE_DOCKER=1` снесёт и его.

## Диагностика

```bash
./remote/tools/healthcheck.sh                          # сквозная проверка

./remote/tools/rexec.sh server 'systemctl status frps' # сервер
./remote/tools/rexec.sh server 'tail -50 /var/log/frps.log'
./remote/tools/rexec.sh server 'docker logs --tail 50 open-webui'

./remote/tools/rexec.sh pc 'ollama ps'                 # ПК (нужен -EnableSsh)
./remote/tools/rexec.sh pc 'nvidia-smi'
```

Если `pc_tunnel_up: false` — почти всегда одно из трёх: ПК спит, `frpc`
не поднялся, или токен на сервере и на ПК разный. На ПК:

```powershell
Get-Process frpc
Get-Content C:\llm-agent\frpc.log -Tail 30
Get-ScheduledTask llm-agent-frpc | Get-ScheduledTaskInfo
```

Отдельная ловушка: `frpc` зарегистрирован как задача от SYSTEM и стартует
до входа в систему, а вот **Ollama на Windows живёт в пользовательской
сессии**. Поэтому после перезагрузки без входа пользователя туннель будет
поднят, а модель — нет, и статус честно покажет `pc_tunnel_up: false`.
Лечится включением автовхода либо запуском Ollama службой.

Отдельно про сон: ноутбук в спящем режиме туннель не держит. Если модель
должна быть доступна круглосуточно —

```powershell
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
```

## Что сейчас открыто наружу

Вы просили пароли пока не ставить — сделано так, но перечислю честно, что
это значит, потому что адрес публичный и его найдут сканеры:

- `http://31.76.72.214/` — чат **без входа** (`WEBUI_AUTH=False`).
- `http://31.76.72.214/ollama/` — API модели **без ключа**.
- Порт 7000 — управляющий канал frp. Вот он **закрыт токеном**, и это
  единственное отступление от «без паролей»: без токена любой желающий
  пробрасывает через ваш сервер произвольные порты, то есть получает его
  в своё распоряжение. Токен генерирует скрипт, запоминать его не нужно.

Сам туннелированный Ollama наружу **не торчит**: в `frps.toml` стоит
`proxyBindAddr = "127.0.0.1"`, порт 11434 поднимается только на локальном
интерфейсе сервера, а публикует его исключительно nginx.

Когда всё проверите, закрывается двумя правками:

```bash
# 1. Логин в чате
docker rm -f open-webui
# тот же docker run, но -e WEBUI_AUTH=True -e ENABLE_SIGNUP=True
# (первый зарегистрировавшийся становится админом; после этого ENABLE_SIGNUP=False)

# 2. Ключ на API
apt-get install -y apache2-utils
htpasswd -c /etc/nginx/.llm-htpasswd ваш_логин
# в /etc/nginx/sites-available/llm, в блок location /ollama/ :
#   auth_basic "llm";
#   auth_basic_user_file /etc/nginx/.llm-htpasswd;
systemctl reload nginx
```

Плюс HTTPS, когда появится домен: `apt install certbot python3-certbot-nginx
&& certbot --nginx`. Пока адрес голый IP, сертификат Let's Encrypt получить
нельзя.

## Состав

```
remote/
├── server/
│   ├── setup-server.sh      # VPS: frps + Open WebUI + nginx + /llm-status.json
│   └── provision-pc.sh      # с сервера на ПК через Tailscale: recon | install
├── pc/setup-pc.ps1          # Windows: Ollama + модель + RAM/VRAM + frpc
└── tools/
    ├── rexec.sh             # одна команда = один коннект = выход
    └── healthcheck.sh       # сквозная проверка, нужен только curl
```

Tailscale нужен ровно один раз — чтобы дотянуться до ПК и поставить туда
`frpc`. Дальше ПК сам держит соединение с сервером, и путь до модели
через тайлнет больше не идёт.

Оба установочных скрипта идемпотентны — повторный запуск ничего не ломает.
